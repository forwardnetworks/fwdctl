# Collection timing: fields, readings and known causes

Reference for `view slow`, `view history` and `view logs` of `investigate-collection-failure`. Checked on a 40,000-device collection; the numbers quoted are from there.

## view slow: the numbers
Forward's per-device collection metrics: collection duration, the slowest command and its duration, source and device type, jump server, and the merged collection-and-processing error (every error class, not only failures), slowest first, with the median, p95 and max. Forward keeps one slowest command per device, not every command, and saves nothing for an imported, forked or partially collected snapshot (then **unknown**).

`stats` gives `sum_ms` (total device time), `collection_wall_ms` and `implied_parallelism` (total device time over the wall time: the average number of devices collected at once; computed for the whole run, not for a `device` filter), the collector's configured concurrency beside it (`stats.collector`; 128 when unset, said so) with the share in use, `by_device_type` and `by_connection` (devices, total and median time, errors; the eight that took the most total time) and `errors_by_type`. The finding carries the headline numbers because a table or CSV rendering prints the finding, not the stats.

Read the parallelism against the concurrency: well under it means the collector's slots are not the limit (a long tail of slow devices, a per-second rate limit or the devices themselves are); near it means the collector is. Seen: 173 devices at once against a configured 1,024, firewalls (2.7% of devices) using 17% of the total device time (98 of 577 hours), median 201 s against 33 s for switches.

`errors_by_type` counts every error class, including devices Forward tags but did not collect (LICENSE_EXHAUSTED was seen on tens of thousands), while the snapshot's collection-failure count (view summary) was seen to leave those out: the two totals need not agree.

`compare_to_snapshot_id` sets a second collection beside this one: `stats.compare` has both sides and the change in total device time, median, p95 and max, devices, implied parallelism, and per device type and connection (the ten groups that changed most), and the finding carries the summary (seen: 575 and 577 hours of device time on two days, but 321 devices at once against 173, medians 31 and 33 s, so the per-device cost did not change and the concurrency did). A baseline with no metrics (a reprocess, an import) is said, not guessed.

There is no per-device command count or sum, so a device whose collection time far exceeds its slowest command (a PAN-OS firewall at 1,500 to 2,100 s with a slowest command of 20 to 80 s) has time Forward does not attribute; the log (view logs) is the only other evidence.

## Idle gaps, the queue and the per-device timeout

`stats.in_flight` is the run over time, from each device's own start time and duration: `in_flight_buckets` (`devices_in_flight` per bucket of 5 minutes, longer for a long run), the peak and when the profile first reached 90% of it, `finished_by_seconds` (when 50%, 90%, 99% and all devices had finished) and `idle_gaps`: stretches of at least three buckets with fewer than one device running, with how many devices started after the longest gap and which connection and type most were (`started_after_the_longest_gap`, with the first ten names). A run can go quiet in the middle and then start a second batch, which the average hides; seen: 31,378 devices started in the first 100 minutes, none in the next 70, then 7,322 mostly Cisco IOS-XE routers. A device's recorded start can be when it was handed to the collector rather than when it got a slot, so the count can exceed the configured concurrency (1,788 in the first five minutes against 1,024); read it as "started and not finished".

`stats.queue` is Forward's own series of devices queued and running over the run (`queue_buckets`), with the maximum queued, running and slots held during the longest idle gap against the concurrency limit. Nothing queued and nothing running is an idle collector; running far below the limit with devices queued means a jump-server or vCenter cap or a dispatch delay held work back. Queued subtasks are never listed by name, and what a queued task waits for is not recorded.

`stats.org_collection_settings` holds the organization's per-device collection timeout (Forward's default 180 minutes), retries, and `devices_that_ran_to_the_timeout`. A gap that ends at the timeout after the run began is said in the finding. `stats.running_in_the_gap` names the collector subtasks in progress in the middle of the longest gap (Forward's own description, status, operation and start). `stats.subtasks_not_succeeded` (read whenever there is an idle gap or a device with no recorded duration) counts the collector task's subtasks by Forward's status and lists the ones that TIMED_OUT, were CANCELED or FAILED with how long each ran (a timed-out subtask's run time should match the per-device timeout; capped at 3,000 subtasks).

A subtask can TIME_OUT although its device's own collection finished within a minute (seen: both subtasks running mid-gap, the devices' logs finished at once, the subtasks timed out 3 h later and held an SD-WAN batch back). The finding names such subtasks. That is a collector issue to raise with Forward, not a slow device.

## Batches: why devices start late

Forward collects interdependent devices as ONE batch subtask: an ACI fabric, F5 or ASA families, a Viptela vSmart with its edges, a controller with the devices it manages. Batches are enqueued longest-estimated first, and a batch starts when all its resources (concurrency slots, one per device, jump servers, vCenter) are free at once. The devices in a batch show start times inside that subtask, so devices that "start late" may be the tail of a batch task that began earlier, or a batch that waited for a resource. This is read from Forward's scheduler source; it is not something Forward records per run.

## Devices with no recorded duration

`stats.no_recorded_duration` lists devices that ended without a recorded collection duration: count, by type, up to 50 named, each with its `start_offset_seconds`. They were cancelled, finished early or never collected; most are not hung. Only the device's log (view logs, `failure` INFO) or `subtasks_not_succeeded` tells which.

## view history

How long each recent collection took, from the snapshots themselves, so it reaches further back than the few tasks `inspect-collection` lists: per collected snapshot its `collection_seconds` and `processing_seconds` (Forward's own figures), `devices` and `devices_change` against the next older collected snapshot (a jump is a change in what is collected, not a slower collector), the devices collected and failed, and, where the snapshot records its collector task, `task_seconds` (the task's start to finish) and `collection_end_to_processed_seconds`. It gives the median and flags any collection more than 1.5 times it (`slower_than_usual`, only when at least four have a duration), and the finding says how the latest compares. The median mixes collections of different sizes, so read it beside `devices`.

Only Forward-collected snapshots count: a reprocess, an import or a prediction is not a collection. A collection whose snapshot was replaced by a reprocess (the task survives) is listed under `collections_without_a_shown_snapshot` with the task's start, end and what its snapshot became, from Forward's recent collector tasks, so a collection older than that window can be missing. It does not wait for a newer snapshot that is still processing.

`longest_idle_seconds` (with where the gap is), `had_idle_gap` and `subtasks_timed_out` are measured for the newest 5 collections only, since the per-device record is large. Each of the 5 rows carries both fields; a value of null means that measurement failed (the row's `notes` say why: metrics missing, no collector task, a timeout reading a large record), never zero. The metrics of a very large collection can take longer than the default 120 s request limit: raise it with `FORWARD_TIMEOUT` (for example `FORWARD_TIMEOUT=10m`) when the notes say the metrics could not be read. `stats.collections_with_an_idle_gap` and `collections_with_timed_out_subtasks` count only measured rows and are null when none was measured; the headline says when the latest collection went idle or had subtasks that timed out, or that it could not be measured. Seen: a collection that went from 52 minutes to 1h47m and then 3h20m as its device count went from about 4,500 to 40,000.

## view logs

A window of one device's collection log at or above a level (`failure`, default WARN), read up to 512 KiB; `device` must be the name the device was collected under. The whole log is scanned (up to 64 MiB) and `log` gives its line count, first line, last line and time, the last 20 lines, and the first lines that mention cancel or timeout, so a device that finished, was cancelled or timed out can be told apart. Give `failure` INFO: at WARN the last line is only the last warning.

## Known cause: PAN-OS external lists

Forward's PAN-OS collector tries `request system external-list show` for each external list, and on an authorization failure downloads each list's URL from the collector instead, repeatedly. A PAN-OS device whose collection time far exceeds its slowest command is often this (log lines "Unable to get external list ... Trying to download from the list's URL directly"; seen one list every 2.5 to 4 minutes, about 16% of the total device time). Forward has no setting to skip it or bound the download; the fix is on the device (permission for that command, or no external lists).

## Would more concurrency or collectors help? (view slow)

The slow view answers it from four stats:
- `what_if`: the lower bound on the run is the longer of the longest device and total device time over the concurrency (slots). If the actual time is within 20% of it, concurrency (or another collector) is what sets the pace and more would shorten the run down to about the longest device. If the run took much longer than its lower bound, slots are not the limit and more of them would not help.
- `idle_slots`: per time bucket, the slots the collector held minus the devices actually collecting. The count of buckets where work waited in the queue while more than half the held slots had no device collecting is the sign that something other than device collection holds slots. `held_by_at_worst_point` groups the collector subtasks in progress at the worst moment by status and operation, so a post-collection step, a retry wait or a resource wait shows if Forward's operation text names it.
- `tail`: the devices still collecting in the last quarter of the run, by device type and connection, with the median and longest collection of each. A few slow device types late in the run (a firewall family) set the end time whatever the concurrency.
- `by_collector`: one row per collector that ran devices: its id and name (the network's default collector, the one attached to the network, is `is_default` and runs every device with no pin), pinned and unpinned devices and device-hours, `finished_at_seconds`, peak in-flight, concurrency and its own lower bound. `by_collector_straggler` names the collector that finished last and when the next one did. Each device row also carries its `collector`, so paging the view (`limit`, `offset`) is a per-device join of collector and `collection_ms`. Collector ids appear as `C101290`, `101290` or a name in different places; here they are one key.
- `rebalance`: what the run's bound would be if the devices with no pin were spread over the collectors that already work on this network (longest first, each to the collector whose finish it grows least): estimated seconds now and after, per collector how many unpinned devices and hours it would run, and the largest example names. It is an estimate of the bound (it ignores ramp-up, jump servers and per-vendor limits) and changes nothing; pinning is `edit-source` object `classic_device`, `collectorId`. If the bound does not move, one slow device sets the pace and more collectors cannot help. `moves` lists the concrete device moves (device, connection, from and to collector, device-hours, how to move it), longest first; `limit` (default 50) caps them, `failure` keeps one connection type, and `edit_source_definition` is the ready `edit-source` batch (`definition.devices`, a list of {name, collectorId}, one dry-run plan) for the classic devices among them. Only devices with no pin move; pinned ones stay.
Each `by_collector` row also has `resources`: that collector's own series over the collection window (CPU load, free memory, queued tasks, tasks in flight against its executor, GC, file descriptors, disk) with a verdict. Queued tasks with CPU near saturation or a full executor is the sign the collector was the bottleneck; queued tasks without either means the wait was not its capacity; nothing queued means it was not the limit. Forward returns these only to a login with its collector-debug permission (DEBUG_COLLECTORS); without it a limit names the permission. Reading the series: `cpu_load` is the system-wide recent load as a fraction (0 to 1; below 0 means not yet measured, and 0 can mean the platform does not report it), not the collector process's share; GC time is a cumulative counter since the collector JVM started (it resets on restart), so only differences mean anything (`gc_seconds_in_window`); free heap is free space inside the heap the JVM has committed so far, so max minus free overstates heap in use; tasks in flight are started minus finished. An unknown collector name is a 400, not a 404. Forward records no network throughput, thread count or per-protocol session series.
Not available: a count of a known cause such as a PAN-OS external-list loop (the per-device log has it: view logs). `subtasks_not_succeeded` reads up to 10,000 subtasks (failed, timed-out and cancelled ones first); `cap_reached` says when that was not enough.

`stats.what_if.at_max_concurrency` is true when the collector's concurrency is already Forward's maximum (1024): the verdict then says more slots per collector are impossible and only more collectors add capacity, and, when slots sat idle while work waited, that the limit is how slots are handed out, not the concurrency. With `compare_to_snapshot_id`, `stats.compare.dispatch` says "same work, different dispatch" when the two collections' device time is within 5% but their wall times differ by more than 5%.

`stats.slowest_commands` (view slow) rolls up the slowest command of each device by its text: devices, total, median, p95 and max of that command's time, `share_of_device_time_percent` and the three most common device types, with `custom_group` naming the custom command group of the network that holds the text (null for a built-in). `stats.slowest_by_custom_group` rolls those up by group. Forward records only each device's slowest command, not every command, so both are a lower bound on a command's or a group's cost; there is no per-command time to sum. `stats.collector_outliers` names a collector whose peak open file descriptors or queued tasks are at least twice the median of the others (three or more collectors read, the resource metrics need the DEBUG_COLLECTORS permission). `stats.slot_time` sets the slot-hours the collectors held (up to: a bucket's slots count for the whole bucket) against the device-hours of collection, and the finding says so.

## Comparing cohorts in one call (view slow)

- `device` takes several names or fragments separated by commas (`"edge1, edge2, vs-"`), matched case-insensitively as substrings, so a cohort is one call.
- Each group in `stats.by_device_type`, `stats.by_connection` and `stats.by_setup` has `share_of_device_time`: its total time over the total of all groups.
- `stats.by_setup` groups the devices by the controller-managed setup that lists them as a controller or managed device, against every other device in one group, so "are edges collected through a setup faster than classic ones" is one read. It is present only when the network has a setup.
- `stats.slowest_commands` totals the slowest command of every device by command, so "which command costs the most" is one read. The metrics carry only each device's slowest command, not every command: what the rest of a slow device's time went to (other commands, queueing) is not in them. The device's log (view logs) has it.

## SD-WAN collection: what controller mode skips (source-read by field sessions; not tested on a live network)

Read these before advising on slow or risky SD-WAN collection. They come from read-only reads of the product source by a field session, with no release dates and no run against a network.

- **Controller mode does not protect vEdges (source-read).** With a vSmart source configured, only the IOS XE SD-WAN edges skip `show sdwan omp routes` (the vSmart's OMP file is copied into each edge snapshot). A Viptela vEdge still runs the full `show omp routes`: its collected-state pipeline sets the OMP routes state unconditionally, and the post-processor copies the vSmart's file only into vEdge snapshots that lack that state, so the vEdge's own output wins and the command cost is paid anyway. Not traced: what happens when a vEdge's command fails.
- **Controller-managed devices are reached at their stored host (source-read).** The vSmart reports vEdge private IPs from its control-connections table; discovery does not rewrite the saved host; the controller entry's jump server is not copied onto managed devices (each managed entry needs its own host and jump server); the connectivity test uses the stored host. A hand-set per-device host is the designed route and does not scale to hundreds of edges. Not traced: collector-side resolution of the managed host.
- **Open:** whether a controller-only `controller_setup` (no managed devices, no migrate) makes the IOS XE edges that stay classic skip the OMP command is not established; do not recommend it as protection until it is read from the code or tested.
- **The OMP route filter that exists is the RIB subnet filter** (`ribRouteSubnets` in the collection settings; empty means a full dump). It applies to IOS XE SD-WAN versions 17.03 up to below 17.15 (from 17.15 it falls back to a full dump with a warning) and to vSmart; it does **not** apply to vEdge. A separate OMP-only filter does not exist.
- **Excluding a built-in command exists:** `edit-platform` area `collection_settings`, name `organization`, `disable_commands` `[{device_type, command, version_start, version_end}]`, from 26.8.3, org-wide, one entry per call, per device type and version range (not per device). The `command` is a regex matched against the whole lowercased command, so `show omp routes` does not also catch `show omp routes 10.0.0.0/8`; use `.*` for forms with arguments. The `device_type` is the source connection type (for example `cisco_ios_xe_ssh`, `viptela_smart_ssh`; for vEdge probably `viptela_edge_ssh`, unconfirmed).
- **Blocking a command is source-read, never run live:** how a disabled command is applied, how to check it on one device and what to read in the log are in `edit-platform` reference/areas.md ("collection_settings: disabled commands"); the OMP routes command on vEdges is the worked example in `edit-source` reference/sdwan-controller-mode.md.
- **Unverified, test on a lab before anyone recommends it:** which `device_type` string fwdctl accepts for vEdge; whether a disabled OMP command leaves an empty state, an absent file or a COMMAND_DISABLED error; whether the vSmart post-processor then fills the edge from the controller (it fills only when the state is absent).
- **Safety:** one field incident had a working-session snapshot run the OMP routes command on many vEdge devices at once, and several remote-site routers crashed. Never run the OMP routes command on edges at scale in a working snapshot; check which workspace or schedule will run it first; prefer controller mode plus `disable_commands` for vEdge once the tests above are done.
- **Investigations should check** for a vManage or vSmart source in the collected network and whether SD-WAN devices are still classic devices (`inspect-collection` view `migration`).
- **Timing example, one network of about 1,200 devices:** the daily collection took about 1h05m, with 99% of devices done in about 20 minutes; 50 devices over 10 minutes each held about half of the device-hours, and `show omp routes` alone was about 9.7 device-hours across 43 devices. The collector was not the limit.
