# Flipping an SD-WAN network to controller-mode collection

Read when someone wants IOS XE SD-WAN edges to stop running the OMP routes command on themselves (the vSmart's file is used instead). **Source-read by field sessions, not tested on a live network**: what an unproven step needs is marked. Forward's own migration wizard has part of the controller information and is not complete, so read it first, then make your own determination.

What controller mode does and does not skip: `investigate-collection-failure` reference `timing.md` ("SD-WAN collection: what controller mode skips"). In short, only IOS XE SD-WAN edges skip the command; a Viptela vEdge still runs `show omp routes`, so controller mode does not protect vEdges.

## Order

1. **What already exists.** `inspect-platform` area `controller_setups` (every network and workspace: controllers, hosts, jump servers, stored login ids, last connectivity test). Reuse what the customer and Forward already configured before proposing a new setup.
2. **The wizard's view.** `inspect-collection` view `migration`: the classic devices Forward says need to move, the controllers found by the devices' last connectivity test (not from a configuration record; `address_confirmed_by_a_record` says when a classic record has the address), the `credential_candidates`, and a `suggested_migrate`. The addresses are what the devices reported (overlay system IPs), not necessarily reachable ones, and a device with no test result is not classified. Its `suggested_migrate` **deletes** the classic devices: use it only as a source of hosts, logins and collection options, never apply it for this.
3. **Coverage from the collected data.** `inspect-collection` view `migration` now returns it as `edge_coverage` (checked read-only against one real network by a field session: edges, edges with a vSmart up, distinct vSmarts, the cover and the edges the wizard misses all matched their hand computation) (below is what it does, so you can check it by hand): An edge receives OMP data only from a controller it connects to and that you added. Read each IOS XE SD-WAN edge's `sdwan_control_connections.txt` (fixed-width `show sdwan control connections` output; keep PEER TYPE vsmart rows whose STATE is up, PEER SYSTEM IP is the third field; STATE is the token after PROXY Yes/No, found from the right, because a row can lack the trailing group id; a vSmart repeats once per local colour, so count distinct edges per vSmart, not rows) for the vSmart system IPs it connects to, then choose the smallest set of controllers that covers every edge (greedy cover works). Note the edges with no vSmart rows, and whether you filtered on connection state. One configured controller makes every IOS XE edge skip the command (source-read), so a controller set that covers only some edges silently loses OMP data for the rest.
4. **Compare** the wizard's controllers with the cover and list the edges the wizard's controllers do not reach.
4a. **Which address is the right `host`.** One field observation, on one controller already collected in a customer workspace (not generalised): the address that worked as the setup's `host` was the controller's management (VPN 512) address, while the address its edges report in `sdwan_control_connections.txt` was its VPN 0 control/transport address, which the data-centre core did not route. So neither the system IP (what the migration view and the wizard list) nor the edge-reported control address is the right `host`. For a controller you already collect, read its `configuration.txt` (`inspect-device-files`): `host-name`, `system-ip`, and the management VPN (`vpn 512`) interface and routes. For a controller you do not collect, Forward has no data that lists its management address that I know of; ask the customer for the SD-WAN manager's controller list (system IP to management IP).
5. **Dry run a controller-only setup** (no managed devices, no migrate): `edit-source` object `controller_setup`, action `create`, `definition: {"name": "<setup>", "controllers": [{"name", "type": "cisco_sdwan_vsmart_ssh", "host", "port", "cliCredentialId", "jumpServerId"}]}`. The vSmart controller type id is `cisco_sdwan_vsmart_ssh` (read from Forward's connection types; `cisco_sdwan_ssh` is the CLASSIC vEdge type). The setup name goes inside `definition`. The dry run does not check the type against the class (a vEdge type validated too), so check the type string yourself. The `host` is the address the collector connects to, so it must be reachable from the collector (an overlay system IP may not be); a jump server is `jumpServerId`. Which stored login works on each controller is not recorded: the connectivity test result says. Reachable addresses and the working logins come from Forward's own records and the customer, not from this skill.
6. **Apply** only with the customer's approval. `apply: true` creates the setup. It is a write on the customer's collection sources. Then queue the connectivity test (`edit-source` `controller_setup` action `test`) and read the result.
7. **After the first collection:** every covered edge should have an OMP file (`inspect-device-files` list), or the missing ones are listed. Unproven until a lab shows it: that a controller-only setup makes the edges that stay classic skip the command, and what an edge's state is when its controller does not cover it.
8. **Undo:** `controller_setup` action `delete`, `confirm` = the setup name (the controller entries go; the edges were never touched).

Starting a collection on a network whose only source is a controller setup: use `edit-collection` (the network-wide start); `edit-source` has no start action. Its pre-check counts controller setups, and a controller-only start has not been run against a live Forward (the dry run says so), so watch it with `inspect-collection` view `status` (`running_now`).

vEdges are unaffected by controller mode: keep their collection disabled, or use `disable_commands` (org-wide; source-read, never run on a live vEdge: see "Example: blocking a command on SD-WAN edges" below), until it is tested.

## Finding the management address by testing candidates (run once by a field session; not generalised)

For finding devices in a subnet in general, use Forward's device discovery (`edit-source` object `discovery`, type `SUBNET_SCAN`; its dry run states the address count). It uses the logins Forward associates and does not return a controller's system IP, so for a vSmart's management address the candidate test below is the one that does. When the controllers' management addresses are not in any collected file, a candidate list can be tested without touching production: `edit-workspace` creates a change workspace (one never-collected placeholder device, a few days, no schedule), then in it `edit-source` `controller_setup` `create` with one controller entry per candidate (type `cisco_sdwan_vsmart_ssh`, port 22, a stored login), then `controller_setup` action `test` with `wait_seconds`, then read each controller's result with `inspect-collection` view `config` (`controller_setups`). Observed once on a real network, over the regional management subnets learned from the OMP routes (51 candidates):
- `HOST_NOT_REPORTING_ANY_GUEST` or `HOST_MISSING_GUEST_RESULTS` on a candidate: a controller-type host answered, but NOT necessarily a vSmart: SD-WAN Manager nodes answer the same SSH test and report no managed devices. Read `name_aliases` in the test result (`inspect-collection` view `config`): for a vSmart it was `[hostname, system IP]`, which maps the management address to the system IP directly (matched the fingerprint method below 10 of 10 on the one network where both were run); a manager shows a manager hostname pattern and no system IP. Do not add managers as controllers (one was added to a production controller-only setup and removed again). The count of vSmart-type answers per region matched the vSmarts the edges connect to there.
- `PING_FAILED`: nothing there. `DEVICE_TYPE_MISMATCH`: the login worked on a host that is not a controller.
- Not resolved by the test: which management address belongs to which system IP. The result has no system IP field; the managed-device sample it returns is a few edge private IPs.

**Where the results are.** `inspect-collection` view `config`, `controller_setups[].devices[].test`. View `connectivity` reads the classic devices' stored tests only: on a workspace holding one placeholder device plus a probe setup it counted only the classic device and did not show the probe setup, so do not read the probe from there.

**A second field run** (19 candidates beside two known controllers): 13 `PING_FAILED`, 6 `DEVICE_TYPE_MISMATCH`, no controller answer, so a range next to known controllers proved nothing about where the missing ones sit.

To read a Manager's own show output (for example `show control connections`, which lists every vSmart with its system IP, site and control address but not its management address), run the command through a CLI endpoint: `edit-source` reference/objects.md, "Running one command on a host".

**Before running:** say how many addresses and which login the test will use, keep the candidates to the controller subnet (not the surrounding range), and delete the probe setup afterwards (`controller_setup` action `delete`) and say that it was deleted.

**Caution:** this uses the stored login against every candidate. `DEVICE_TYPE_MISMATCH` means the login worked on a host nobody confirmed. Test only a short list the customer has approved, never a whole subnet by default, and leave the test workspace and its setups for the person to remove (the workspace expires; `controller_setup delete` removes a setup).

## Mapping each controller's system IP to its management address (fingerprint method; run once by a field session, sanitized)

Use when the candidate management addresses answer as vSmart-type hosts (the section above) but nothing says which answers for which system IP. It needs no new collection and no customer question: every input is saved data. Not generalised beyond one network; read-only apart from the test setups in the workspace.
1. **Candidates.** The management subnets are the prefixes the head-ends learn as OMP or system-interface routes from the cloud hub edges (`vrf_routing.txt`, `sdwan_omp_routes.txt`); the edges' control addresses fall in the matching transport subnets and are not reachable from the collector. Test the management subnets (skip network, broadcast and gateway addresses) with controller-only setups in a test workspace and `controller_setup` action `test`: `HOST_MISSING_GUEST_RESULTS` or `HOST_NOT_REPORTING_ANY_GUEST` is a vSmart-type host, `PING_FAILED` is nothing, `DEVICE_TYPE_MISMATCH` is another SSH device (the login worked there; see the caution above).
2. **Fingerprint.** For each answering candidate read its FULL reported managed-device list: `inspect-collection` view `config` with `device` naming the controller entry, paged by `limit` and `offset`. Take each IOS XE edge's interface IPv4 addresses (an NQE over interfaces and subinterfaces with their `ipv4.addresses`) and the edge's own `sdwan_control_connections.txt` (vSmart system IPs with STATE up). Edge E is in candidate C's list if and only if E connects to C's system IP, so for each candidate the set of edges whose addresses appear in its list should equal the set of edges connected to one system IP. Match the sets by overlap (Jaccard).
3. **Pitfall that matters.** Use only interface addresses that belong to ONE edge. Exclude addresses shared by several edges and the whole 192.168.0.0/16: shared private addresses gave false matches (a controller that truly served 9 edges matched 18). With unique addresses the match was exact.
4. **Validate first, without new data.** One controller that is already collected has its own `sdwan_control_connections.txt` listing each edge's system IP and private IP; it gave exactly the edge set the edges' files predicted (9 of 9, no extras) before the method was trusted on the rest.
5. **What it resolved once:** 7 of 10 controllers matched exactly, 3 matched one system IP clearly best (one with 3 of 4 edges; two with all edges plus one extra). Controllers whose hosts answer but report no managed devices cannot be fingerprinted, so their system IPs stay unmapped and the edges that connect only to them stay uncovered by the others.

The matching is mechanical but is not a skill yet (a view taking the candidate lists and the snapshot and returning the mapping and the uncovered edges is possible; the NQE and the overlap scoring would be its two parts). Leave the test workspace and its setups for the person to remove.

## The classic-to-controller migration, step by step with checks (field-run once; dry run only, nothing applied)

Forward's wizard (`inspect-collection` view `migration`) is the first read, not the plan. Use it, then correct it where it falls short. A migrate DELETES the classic records it names, so every step below ends in a check before the next.

1. **Read the wizard fully.** `inspect-collection` view `migration` with `limit` large enough (`devices` is paged at 50 by default; `limit: 200` returned all 85 records of the network this was run on). Check: `devices_counted` equals the number of `devices` rows you hold. Each row has `name`, `effective_type`, `host`, the login ids, `jump_server_id`, `collector_id` and `options` (the collection flags). (`migration_plan` already builds that input for all devices, with `controllers` empty to fill; review its `review` block. Checked once on a real network against a hand-built input: identical.) **Build `managedDevices` from `devices`, not from the per-controller `suggested_migrate`:** the suggestions are capped to a pilot per controller, put each device under one controller only (a setup lists every controller once) and covered 78 of the 85 devices there (devices with no controller in their test result are in no suggestion).
2. **Do not take the wizard's controller entries.** Their `host` is the system IP and the name is a placeholder. Find the reachable management addresses and the system IP of each (the sections above): candidates from the OMP-learned management prefixes, controller-only test setups in a test workspace, `name_aliases` for the hostname and system IP, `edge_coverage` for which vSmarts the edges connect to. Check: every vSmart you add answers the test as a controller and is NOT an SD-WAN Manager (manager nodes report no managed devices and a manager hostname).
3. **Choose the controller set by coverage, from the edges' live control connections.** The controller to configure for an edge is a vSmart it is **up** to in its own `sdwan_control_connections.txt` (`edge_coverage`: per edge `edge_vsmarts_up`, plus the minimal cover), NOT the `controllers` that `inspect-collection` view `migration` lists from each device's last connectivity test. One field workspace listed two edges under the vSmart it used although neither had an up connection to it, and those two received no shared OMP file while the two edges that were connected to it each got its 206 MB OMP routes file. An edge a configured vSmart does not reach gets no OMP data from it. **Put every vSmart an edge is up to in the SAME setup as the edge** (let `edge_vsmarts_up` choose which vSmarts go in that setup): in one field workspace with the vSmarts split over two setups, the edges whose up vSmart was in the other setup got no OMP routes file although that vSmart collected and listed them as up; recreating one setup holding all three vSmarts and the edges gave all four IOS XE edges an OMP file (about 189 and 206 MB, each from its own vSmart). Observed once and not explained from the source, so treat a split layout as a risk and check the edges' OMP files after the first collection. `edge_coverage` (state up): the minimal cover, and the edges your chosen controllers do not reach. Check: list the uncovered edges. Once any vSmart is configured, every IOS XE edge in the network skips the OMP command (source-read), so an edge that connects only to controllers you did not add loses its OMP data. Say which edges those are and what is missing (for example controllers not found in the scanned addresses).
4. **Carry the collection flags exactly.** Restate `collect` and the options from each record (the migration view's `options`). Check, in the dry-run review, every vEdge whose `collect` is not false: vEdges that the customer switched off after the OMP command crashed routers (`collect: false`) must stay false; an unset `collect` (null) means collected. A restated `collect` that is wrong re-enables collection on vEdges.
5. **Capture what the migrate deletes and does not carry.** The classic records (kept from step 1), their test results and their tags. Tested once in a test workspace with a real migrate of 2 edges: **all tags were gone from both devices afterwards** (`edit-device-tags` dry run showed the pairs differing), and `edit-device-tags` action `add` re-applied them (a second dry run said already in the requested state); **locations survived** (the location's assigned-device list still held both devices: they are stored by device name, nothing to redo). So before the migrate record the tags per device (an NQE over devices for `tagNames` from a snapshot that still has them), and after it re-add them. Tag and location reads come from a snapshot, so check with an `edit-device-tags` dry run after the migrate. Check: you hold the before-records and the tag list for every device in the migrate.
6. **Remove duplicates first.** Existing controller-only setups that already hold the controller hosts, or a setup with the same name, collide: `inspect-platform` area `controller_setups` lists them; delete them (`controller_setup` action `delete`, confirm = the name) before the migrate. Check: no setup in the network holds these hosts or this name.
7. **Dry run the migrate** (`controller_setup` action `migrate`, `definition` with `name`, `controllers`, `managedDevices`; apply needs `confirm` equal to the setup name). The dry run lists the classic devices it would delete. Check: the count equals the devices you meant, no vEdge is switched on by mistake, and every managed device has a login.
8. **Apply a pilot first**, test (`controller_setup` action `test`), read the results, then the rest; after the first collection check that every covered edge has an OMP file and that tags are back. There is no undo command: recreate the classic devices from the saved before-records.

**Not every vSmart is reachable from the collector's side.** In the network this was run on, the whole range one regional management prefix covered held only the SD-WAN Manager nodes (aliases with a manager hostname pattern, `HOST_NOT_REPORTING_ANY_GUEST`) and one other SSH device, and no vSmart; the two vSmarts that three edges depend on were in no prefix the head-ends learn from OMP (their management network is elsewhere or not routed from the collector). `name_aliases` on the test result is how to tell a vSmart (a vSmart hostname and its system IP) from a Manager. Since every IOS XE edge skips the OMP command once any vSmart is configured, an edge that connects only to controllers you could not add ends up with no OMP file: list such edges (`edge_coverage`) before applying.

## Example: blocking a command on SD-WAN edges (source-read; nothing run on a live device)

The general mechanism, how it matches and how to check it on one device is in `edit-platform` reference/areas.md, "collection_settings: disabled commands". This is one use of it. The OMP routes command can crash vEdges when many run it at once; vEdges connect with the `cisco_sdwan_ssh` connection type, so an entry for that type affects vEdges only: `edit-platform` area `collection_settings`, name `organization`, `disable_commands` `[{"device_type":"cisco_sdwan_ssh","command":"show omp routes.*"}]`. The pattern is written lower case and matched against the whole command, so `.*` covers `show omp routes`, `show omp routes {prefix}` and `show omp routes family ipv6`; `show omp peers` is a separate command and is not blocked. Model impact: there is no vEdge parser for the OMP routes file. vEdge forwarding entries come from `show ip route` and `show ip fib`, where OMP-learned routes already appear with ipsec next hops, and Predict's OMP data for a vEdge is built from configuration (site ID, system IP, VPNs, control peers); only the IOS XE OMP parsers read an OMP routes file. So the block is expected to empty only the raw file, which matters to NQE checks that parse command text (`author-nqe-query` reference/config-patterns.md, SD-WAN). Unproven: nothing here has run on a live vEdge, so treat it as a hypothesis until the one-device check in the edit-platform reference passes.

## What one controller-mode workspace test measured (one field run; not generalised)

A workspace with 4 IOS XE edges and 1 vEdge as managed devices and one vSmart as the controller, collected from the UI: the IOS XE edges collected in 43 to 78 seconds (slowest command `show sdwan running-config`, 5 to 6 seconds), where the same kind of edge as a classic device took 1,132 seconds, nearly all `show sdwan omp routes`. The cost moved to the vSmart: 1,075 seconds, with `show omp routes` at 1,056 seconds; total wall time 18 minutes. Only the two edges that were connected to that vSmart got its OMP routes file; the other two and the vEdge got none. The IOS XE edges' forwarding entries matched a production snapshot taken about 40 minutes earlier, apart from one row of tunnel churn (after ordering the next hops inside each row before diffing; see `author-nqe-query` reference/config-patterns.md).
