## The secret file

One file or one environment variable per call. For CLI and HTTP credentials and jump servers it holds the single secret as plain text (a trailing newline is ignored). For SNMP v3 it holds a JSON object: `{"password": "<auth password>", "privacyPassword": "<privacy password>"}`; for SNMP v2c it is the community string as plain text. The file must not be readable by group or others (`chmod 600`). The value is read only when `apply` is true.

## credential

`type` CLI takes `username`, `kind`, `privilegeLevel`, `privilegedModePasswordId` (an id of a stored privileged-mode password, not a password) and `autoAssociate`.

**CLI kinds** (Forward's CliCredentialType; `kind` is checked at the dry run, case does not matter):

| `kind` | What it is | Takes |
|---|---|---|
| omitted or `LOGIN` | the login (SSH or Telnet) | `username` (required); `privilegedModePasswordId` links a stored enable password so devices that need one use it |
| `PRIVILEGED_MODE` | the enable (privilege escalation) password of Cisco-like devices; on Checkpoint a TACACS privilege escalation | `privilegeLevel` (the enable level, the highest when absent; on Checkpoint the TACACS level; on HP Comware the super level); no username |
| `EXPERT_MODE` | Checkpoint expert mode | no username |
| `SHELL` | Avi controller shell | `username` (required) |

Examples (the secret is `secret_file` or `secret_env`, never in the definition): a login `{"type":"CLI","name":"lab-login","username":"admin"}`; an enable password for a Cisco-like device (an IOS or EOS style) `{"type":"CLI","name":"lab-enable","kind":"PRIVILEGED_MODE","privilegeLevel":15}`; a Linux host over SSH is an ordinary login `{"type":"CLI","name":"linux-login","username":"ops"}`. `privilegeLevel` is refused on any kind but PRIVILEGED_MODE and `privilegedModePasswordId` on any kind but LOGIN.

**Pairing a login with its enable password.** Two ways, both in Forward's model: (1) create the PRIVILEGED_MODE credential, then create the LOGIN with `privilegedModePasswordId` set to its id, and every device that uses that login and needs an enable password uses it; (2) set the device's second credential (`cliCredential2Id` on the device, where this skill supports it) so the one device uses that enable credential. A device's own setting wins over the one stored on the login. Which vendors need an enable password is decided by Forward's device type, not by this skill: an unset credential is auto-associated only if the credential allows it (`autoAssociate`, default true).

HTTP credentials: `loginType` is one of LOCAL, RADIUS, TACACS, OAUTH, JWT, SAML; the HTTP credential `kind` is LOGIN or API_KEY (an API key for devices such as firewalls that authenticate by key). HTTP takes `username`, `loginType`, `autoAssociate`. SNMP takes `version` V2C or V3, `port`, `timeoutSec`, and for V3 `authUsername`, `authType` (MD5, SHA, SHA_256, SHA_384, SHA_512) and `privacyProtocol` (DES, AES_128, AES_192, AES_256); V3 requires a username, and a privacy password requires an auth type. Forward returns only an id for the stored secret. Delete needs the credential's id and type and `confirm` equal to the id.

## jump_server

A jump server authenticates by key (the secret is the private key; `sshCert` is an optional public certificate, not secret) or by password. `port` defaults to 22. `update` (by id) changes the fields given, and optionally rotates the password or key from the secret; `delete` needs `confirm` = the id and stops collecting the devices that go through it. A change makes Forward re-handle those devices.

## proxy

A proxy has no secret. `create` needs `name`, `host`, `port` and `protocol`; `update` replaces all of a proxy's fields, so restate them. The SDK has no proxy delete.

## classic_device

A device in the list Forward collects (CLI/SNMP/HTTP devices). `create` needs `name` and `host`; an enable password is the device's **second credential** `cliCredential2Id` (a PRIVILEGED_MODE credential; `cliCredential3Id` is EXPERT_MODE for Checkpoint); per-device collection options (`enableSnmpCollection`, `collectBgpAdvertisements`, `bgpTableType`, `bgpPeerType`, `bgpAndBmpFailureHandling`, `disableIpv6Collection`, `fullCollectionLog`) are checked against Forward's enums, and a BGP table or peer type needs `collectBgpAdvertisements: true` or Forward drops it. `update` can change every one of these, including the SNMP credential and the jump server. credentials and the jump server are given by id (`inspect-platform` areas `credentials` and `jump_servers`). `collectorId` pins the device to one collector of the org (numeric id such as `C42` or `42`, not the collector UUID); without it the network's default collector is used. `update` can move a device to another collector. `update` changes host, type, port, the CLI and HTTP credential, `collectorId`, `collect` and `note` (it patches); the SNMP credential, jump server and extra CLI credentials cannot be changed in place, so delete and re-add. `delete` removes it from the list (`confirm` = its name); past snapshots keep it. Nothing here touches the device.

**Many devices at once.** `update` with `definition.devices`, a list of `{name, ...fields}` (the fields of a single update, for example `{"name": "r1", "collectorId": "C101291"}`), and no `name`. Devices that get the same change are sent in ONE request (Forward's batch patch: one transaction, so every device in that request changes or none does; a bad credential, jump server or collector id fails the whole request; up to 2,000 names to a request), so pinning thousands of devices to a few collectors is a few requests, not thousands. Names match case-insensitively; a name that is not in the device list is skipped and named. The dry run lists each device's change (only the fields that change, not blanks) with a count by target collector and the number of requests; the client library retries a transient failure (a TLS handshake timeout, 429/503, and, because re-applying the same patch is safe, 502/504 and a reset) up to 4 attempts with backoff. A rate-limit lockout (only where the deployment enables API rate limiting) is not retried: the failure line says how long the login is locked out. A request that still fails leaves its devices unchanged and the result says how many were applied; running it again re-applies only what is not yet as asked. Up to 10,000 devices per call. To read the devices and their current collectors first, `inspect-collection` view `config` with `collector` and `names_only`.

**Unsetting a field.** `definition.clear` (a single update, or inside a `devices` entry) lists properties to reset to unset: `collectorId` (unpin from a collector: the device then runs on the network's default collector), the credential ids, `jumpServerId`, `note`, `port` and the collection options. Leaving a field out never clears it. `bgpTableType` and `bgpPeerType` count only when `collectBgpAdvertisements` is true in the same change. `cliCredential2Id` must name a PRIVILEGED_MODE (or Avi SHELL) credential and `cliCredential3Id` an EXPERT_MODE one.


`test` queues a connectivity test of a small named set of classic devices (`definition.names`, at most 100): it probes each host from its collector, so it is a dry run until `apply`, which needs `confirm` equal to the number of devices. A stored result keeps its old time until the new test replaces it: use `wait_seconds` or compare `tested_at` with the queue time.

## endpoint

A network endpoint is a host or device Forward collects that is not a classic network device: a Linux host over SSH (type CLI), an SNMP device or an HTTP device. `create` needs `name` and `host`; `credentialId` (a CLI login from `inspect-platform` area `credentials`) and `profileId` (an endpoint profile, for example a CLI profile made with `edit-platform` area `endpoint_profiles`; `inspect-collection` view `config` lists them) are ids. A CLI endpoint takes `protocol` SSH or TELNET and may use a `jumpServerId`. A create is idempotent by name: the same host, credential and profile again is reported as already done; a different definition is refused (use `update`). Collection runs the profile's commands only if the organization approved them.

### Running one command on a host and reading its output

Forward has no ad-hoc "run this command" call; a CLI endpoint is how a command is run through Forward on a host that is not a classic device (a Linux host, a manager or any SSH host the CLI login works on), without logging in outside Forward. Do it in a workspace network (`edit-workspace`), not production.
1. **Profile.** `edit-platform` area `endpoint_profiles`, action `create`, `definition.type` CLI, `command_sets` `[]` and `custom_commands` with the command. The dry run reads Forward's approved-command list and names any command it has not approved (nothing is saved), so it is also the check that the command is allowed. The profile is **organization-wide**: give it a distinct name.
2. **Endpoint.** `edit-source` object `endpoint`, action `create`: `name`, `host`, `protocol` SSH, `credentialId` (a CLI login), `profileId`, optional `jumpServerId`.
3. **Collect.** The command runs at the network's next collection (`edit-collection`, dry run first; it collects every source in that network). **A network whose only collectable item is an endpoint may not collect at all:** in one field workspace (every classic device `collect=false`, one CLI endpoint) the collection ended FAILED about 13 seconds after the connectivity tests passed, with no start time, no snapshot and no reason readable through the task API. It is believed, not confirmed, that the network needs one enabled classic device even if it can only fail: if so, add a throwaway `classic_device` on a documentation address (a TEST-NET address such as 192.0.2.1) in the workspace, expect that device to show as failed, and remove it afterwards. `investigate-collection-failure` view `summary` with `collector_task_id` shows the task's note and failed subtasks when the API has them. It takes no connectivity-test entry: `inspect-collection` view `connectivity` counts no tested device for it.
4. **Read.** The output is in `network.endpoints` as `cliCommandResponses` (`command`, `response`), read with `fwdctl nqe run` (`fwdctl context schema cliCommandResponses` lists the fields; `collectionError` and `status` are not fields of the response record). Not in the device files.
5. **Clean up.** `edit-source` `endpoint` `delete`, then `edit-platform` `endpoint_profiles` `delete` (confirm = the profile id), and say so.
Confirmed once in a field workspace (a CLI profile with three show commands on an SD-WAN Manager: all three ran at the next collection and their output was readable this way); not run here.

## schedule

A collection schedule is days of the week (0 Sunday to 6 Saturday) plus either `times` (HH:mm) or `periodInSeconds` (with optional `startAt`, `endAt`), in a Forward time zone (UTC and about fifty regional IDs such as America/Chicago). `update` REPLACES the whole schedule: restate every field. A duplicate schedule is refused by Forward. Forward does not return the next run time.

## cloud_account

An AWS, Azure, GCP (and similar) account Forward collects. `create` takes the non-secret settings in `definition` and the secret from the secret file: plain text is the AWS secret access key or Azure client secret; a JSON object may carry `password`, `privateKey` (a GCP service-account key) or `apiKey`. `rotate` replaces the stored credentials of an existing account (the earlier secret cannot be read back); `test` asks the collector to try the connection and records a result per region (`inspect-collection` view `config` shows it); `delete` needs `confirm` equal to the name. `update` changes only `collect`, `accounts_enabled` (member accounts of a plain assume-role account) and `c2s_accounts` (the portal account list of a C2S Access Portal account); it sends a partial patch and never restates the credentials. Other settings of an existing account (regions, proxy, concurrency) are changed in the Forward UI: this skill does not restate a whole account, because a partial restatement can clear its credentials. Controller-managed (ACI, SD-WAN) and Mist setups are not covered here yet.


**AWS member accounts (multi-account assume-role setups).** `update` also edits the member accounts one batch at a time, in its own call (with `accounts_enabled` at most):
- `accounts_external_ids`: the account ids (12 digits) whose External ID to set or clear. The values come from `secret_file` (mode 600) or `secret_env` as a JSON object `{"<account id>": "<external id>", "<other id>": null}`; `null` clears. Every listed id needs an entry and no other entry is allowed, so only the listed accounts are touched. A duplicate or unknown id is refused. The values are never shown or returned; the result says `set` or `cleared` per account. A dry run without the values file still checks everything else.
- `accounts_add`: ids of newly discovered accounts (accounts the latest snapshot saw that the setup does not list) to add, each with the setup's own role (`arn:aws:iam::<id>:role/<the role name every member shares>`), enabled, named as Forward discovered it; or `add_newly_discovered: true` for all of them. An id that is already a member or is not newly discovered is refused. A setup whose members use different role names has no single role to give and is refused.
- The member list is replaced as a whole on Forward, so every other account is resent exactly as it was (role, enabled flag, external id, last error), and the account is read again right before the write; there is no compare-and-swap, so a change made in the same instant elsewhere can still be lost. The read-back checks the touched accounts. Not for a C2S Access Portal setup (it has no member accounts; use `c2s_accounts`).

## rapid7_source
A Rapid7 vulnerability source of the network. Its login is a credential that already exists: give its id as `credentialId` (`inspect-platform` area `credentials`); no secret is read for this object. `update` replaces the source, so restate `baseUrl` and `credentialId`. There is no delete: set `collectionDisabled` to stop collecting. The read-back checks the URL and the disabled flag; it does not test that Rapid7 accepts the login.

## controller_setup
A controller-managed setup: controllers Forward logs in to, and the managed devices they report. Logins are existing credential ids (`cliCredentialId`, `snmpCredentialId`, `jumpServerId`; list them with `inspect-platform`), so no secret is read. `update` sets the whole `managedDevices` list (restate every device you keep) and/or moves the setup's one collector (`collector_id`) or unpins it (`clear_collector`). `delete` needs `confirm` equal to the name and stops collecting the devices it manages. `migrate` is Forward's atomic move of classic devices into a new setup (what `inspect-collection` view `migration` counts): it creates the setup and, in the same call, DELETES every classic device named as a controller or managed device, with its settings, test results and tags. The dry run lists exactly which classic devices (name, type, host, collector, credentials) would go, refuses a managed device with no `cliCredentialId` (nothing is inherited from the controller; the view's `credential_candidates` lists logins to try, the working one cannot be inferred), and the apply needs `confirm` equal to the setup name. It is not undone by `update`: recreate the classic devices from the before list. List only a few managed devices first as a pilot and run a connectivity test before moving the rest. `collectorId` in the definition sets the setup's one collector (a setup has one for all its controllers and guests; each migrated device's own pin is dropped, and the dry run names the pins it would drop). `test` queues Forward's connectivity test of every controller and managed device of the setup named in `name` (nothing is sent in a dry run); `definition: {"wait_seconds": N}` (at most 600) waits until every device has a saved result newer than the queue time and returns them (a wait that runs out is reported as the read-back not showing fresh results; repeating a test is harmless); otherwise read the results with `inspect-collection` view `config` (`controller_setups`). Forward publishes the route as experimental. Forward lists an empty set on some deployments that do not support the feature, so an empty list from `inspect-platform` area `cloud_setups` is "none or unsupported".

## mist_setup
A Juniper Mist setup. `region` is one of `GLOBAL_01`-`GLOBAL_05`, `EMEA_01`-`EMEA_04`, `APAC_01`-`APAC_03`; `apiKeyId` names an existing credential. Create and delete only (the API has no update): to change one, delete and create. Neither tests the key; run a collection and read `inspect-collection`.

## custom_command_group
A network's custom command group: the CLI commands (or SNMP OIDs) it adds to a device type's collection. It is NOT a Forward built-in, and the org-wide `edit-platform` `disable_commands` is not how it is stopped (that can skip its commands only silently and only in interactive CLI sessions). `create` takes `definition` `{name, deviceConnTypes, commands | oids, devices, disabled}` (exactly one of commands and oids; empty `devices` = every device of the types; names unique ignoring case) and is checked with Forward's own validation first, so a command the device type refuses is named in the dry run and nothing is sent. `update` (name = the group) is partial: only the fields given change, `commands`/`oids` replace the whole list, and `disabled: true` stops a group without deleting it. `delete` needs `confirm` equal to the name. Undo: delete the created group; update back; recreate a deleted group from the before values. List the groups and find which one holds a command with `inspect-platform` area `custom_command_groups` (`command`). Needs EDIT_CUSTOM_COLLECTION_GROUPS (read: VIEW_CUSTOM_COLLECTION_GROUPS).

## discovery
Forward's device discovery. **`start` scans the network from a collector** (or probes cloud setups), so it is a dry run that says so and applies only with `confirm` equal to the discovery type. `definition` `{type: SUBNET_SCAN | SEEDED | DIRECT | CLOUD, collector_id (default: the network's default collector), ...}` with, for SUBNET_SCAN, `subnets`/`hosts` (one is required), `subnets_to_skip`, `hostnames_to_skip`, `jump_server_ids`, `try_direct_connection`, `protocols` (HTTP, HTTPS, SSH, TELNET, SNMP), `connection_scan_ports`; for SEEDED, `seed_devices` (IPs), `snmp_credential_id`, `jump_server_id`, `recursive`, `allowed_subnets`, `subnets_to_skip`, `hosts_to_skip`; DIRECT takes nothing; CLOUD takes `setup_ids`. The dry run states how many addresses a SUBNET_SCAN reaches (IPv4 subnets and hosts; IPv6 is not counted), the least time that takes at the organization's scan rate limit (`maxScanConnectionsPerSecond`), and why to keep the range to the subnet you mean (hosts nobody confirmed can accept a stored login; failed logins can trip lockouts), and and refuses when a discovery is already running (Forward answers 409). `stop` ends the running discovery (confirm `stop`); what it found stays listed. `add_discovered` (`definition.names`, at most 50) adds discovered devices as classic devices with the type, host, credentials and jump server discovery recorded, each pinned to the collector of the job that found it; the dry run lists them, a device with no host, no inferred type or already collected is refused, and apply needs `confirm` equal to the count. `schedule_create` (`name`, `enabled`, `type` SUBNET_SCAN, SEEDED or DIRECT and its params, optional `schedule`: weekly `days_of_the_week` [0=Sun..6] + `times` [HH:mm], or monthly `day_of_the_week` + `week_of_the_month` [1-4] + `time`, with `time_zone`; no schedule = after every collection) and `schedule_delete` (`name` = the id) manage scheduled discovery, which scans repeatedly from the network's default collector; both need `confirm` (the schedule name, the schedule id). Read jobs, devices found and schedules first with `inspect-collection` view `discovery`. Needs MANAGE_COLLECTION_SOURCES.

**What a controller or managed device entry takes, and what a migrate does not carry.** Each entry takes `name`, `type`, `host`, `port`, `cliCredentialId`, `cliCredential2Id` (privileged mode), `cliCredential3Id` (expert mode), `httpCredentialId`, `snmpCredentialId` and `jumpServerId`. An API-collected controller (a Versa Director, an APIC) logs in with `httpCredentialId` (its `H-…` id), not `cliCredentialId`. A migrate deletes the classic records and adds the setup exactly as sent, so it carries nothing over: restate each record's logins, jump server and port (`inspect-collection` view `migration` builds that input), or Forward tries to auto-associate a login. The collection options of a classic record (note, collect, SNMP and BGP advertisement collection, BMP station, pagination, terminal width, prompts, thresholds) are taken by the same entries under their wire names, so restate those too (`inspect-collection` view `migration` reads them off each record); test results and tags cannot be carried. Source: Forward's source, relayed by the SDK; not run against a network here.
