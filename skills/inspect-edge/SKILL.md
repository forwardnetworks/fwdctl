# inspect-edge

## Intent

A network meets what it cannot collect (the internet, a provider, a partner) at its edge, where default routes point at next hops no collected device owns. This skill finds those handoffs from the model, so the question "where should the internet attach"
is one call, not a hand-written set of queries. It is the feed for `plan-synthetic-device` step 3 (the attachment points) and for the connection rows of an internet node.

## Views

`view` picks the question: `exits` (the default; where the network hands traffic off), `public_addresses` (which public IPv4 addresses the network's own equipment carries) or `trace_sources` (which devices are good sources to trace from). Every view takes `network_id`, `snapshot_id` and `vrf`; the rest are per view, and **an input that belongs to another view is rejected by name**.

| `view` | Inputs it takes (besides `network_id`, `snapshot_id`, `vrf`) |
|---|---|
| `exits` | `device` (narrow), `include_owned` (also list the handoffs to modelled devices; by default only their count), `limit` (default 40, at most 200) |
| `public_addresses` | `device` (exact name), `role` (`management`, `loopback`, `customer_facing`, `internet_facing`, `unknown`), `limit` (default 50, at most 200), `offset` |
| `trace_sources` | `target_ip` (**required**: the control address a good source must reach), `exclude` (device names to skip, such as the edge itself), `candidates` (how many to trace, default 12, at most 30) |

The sections below are the view `exits`; the views `public_addresses` and `trace_sources` follow them. See `schema.json`.

## Procedure

1. Read the snapshot; none ready is **unknown**.
2. Read every IPv4 default-route next hop (per device and VRF) and every modelled interface address (paged, bounded).
3. A next hop is **owned** when a modelled interface carries it, or a BGP neighbor record on the other side proves it (`owner_proof` says which); the rest are **exit candidates**. Group by VRF and next hop: the devices using it, the egress (sub)interface and the local address on it.
4. Read the synthetic nodes (internet node, intranet nodes, L3 VPNs, L2 VPNs, adjacent networks: stored connections and the connections their NQE queries generated) and say, per exit, which node claims its uplink.
5. **ok** with the exits, **unknown** when no default route with a forwarding next hop exists (the edge may be reached by specific routes).

## Who claims an uplink

`claimed_by` is on each exit (and each owned handoff with `include_owned`): `{kind, node, uplink, gateway, vlan, vrf, source}` for the synthetic node connection that claims the exit's egress, or `null`. `source` is `manual` (a stored
connection) or `query` (generated by the node's NQE query). A connection claims an egress when its `uplinkPort` or `gatewayPort` (device and port) is that egress, or the egress is a subinterface `<port>.<vlan>` of the connection's uplink
and the connection's VLAN is that number (`po1000.698` is claimed by uplink `po1000` with vlan 698, or by gateway `po1000.698`). When more than one node claims the same egress, `claimed_by` is the first and `double_claim` lists every
claimant; Forward's behaviour for a double claim is not documented, so treat it as a likely mistake. The evidence has `exits_claimed` and `exits_unclaimed`. **An unclaimed likely internet edge is a Missing Peer**: traffic that
reaches it ends at Forward's `<device>-missing-peer` marker (see `investigate-reachability`) until it is modelled with a synthetic device (`plan-synthetic-device`). A node kind this Forward does not serve is a limit (an exit shown
unclaimed may be claimed there), never an error. An exit with no resolved egress cannot be told (`exits_claim_unknown`).

**Basis of the claim data.** The synthetic nodes are read **as configured now** (every exit carries `claimed_by_basis: "nodes as configured now"`). A snapshot used the node configuration valid when it was **created**, and Forward's API does not expose which version that was (a node has no version or valid-from field), so a node changed after the snapshot was created makes the claim state differ from what the snapshot used. Therefore:
- for the **newest processed** snapshot `claimed_by`, `double_claim`, `exits_claimed` and `exits_unclaimed` are kept, labelled with the basis;
- for **any other** snapshot (an older one, chosen with `snapshot_id`) who claimed each exit in it is **unknown**: each exit says `claimed_in_snapshot: "unknown"` (and `double_claim_in_snapshot: "unknown"` when nodes now double-claim it), the current data moves to `claimed_by_now`, `double_claim_now`, `egress_not_claimed_now`, `exits_claimed_now` and `exits_unclaimed_now`, and the finding says it describes the nodes now, not that snapshot. To learn what an older snapshot did, trace a flow on it (see `plan-synthetic-device`).

`fwdctl nqe synthesize internet --network ID [--vrf V] [--device D]` turns this analysis into a ready internet-connection query (see `plan-synthetic-device` step 4).

## Limits worth stating

`likely_internet_edge` marks an unowned, public next hop with an eBGP session to an unmodelled peer in its connected subnet; it is a hint, not proof, and it is unreliable on a network whose internal WAN uses public address space. Each likely edge carries `confidence` (high, medium, low) and `confidence_reasons`: a public peer AS, a peer that sent exactly one prefix (consistent with a default only) and a VRF named inet/internet each add a point (2 high, 1 medium); a private peer AS (64512-65534, 4200000000-4294967294) with a null received count is always low, whatever the VRF is called (the name is a hint, not evidence). Received counts are null when the model has no received-prefix statistic for the session, which removes the default-only signal; the limits say how many. `likely_edge_groups` folds the likely edges into one row per (VRF, peer AS) with `likely_edges`, `devices`, `peer_as_class` (private, public, own), `vrf_hint` (internet, edge for dmz/public/transit, wan), `received_null_on` and `confidence`, best first; read it before the single rows. `egress_unresolved` says no interface subnet holds the next hop. The finding and evidence name the snapshot read. Only default routes are read; the installing protocol is not in this model; an unowned next hop may be an uncollected device or an address the model lacks; hops that drop, receive, are VRF-forwarded or recursive are left out (counted).

## Evidence

One `nqe` item: `default_route_rows`, `handoffs_total`, `exit_candidates`, `exit_candidates_by_vrf` and `exits` (each: `vrf`, `next_hop`, `devices`, `device_names`, `egress`, `local_address`, and where present `likely_internet_edge`, `confidence`, `confidence_reasons`, `bgp_peers_unmodelled`, `egress_unresolved`, `next_hop_owner`, `owner_proof`, `claimed_by`, `claimed_by_basis`, `double_claim`, `egress_not_claimed`, or for a snapshot that is not the newest `claimed_in_snapshot` and the `_now` forms), `snapshot_id`, `likely_internet_edges`, `likely_internet_edges_by_confidence`, `likely_edge_groups`, `exits_claimed`, `exits_unclaimed`, plus `owned_handoffs` or their count.

## Output

The envelope in `schema/skill-result.schema.json`.

## View public_addresses (the retired `find-public-addresses` skill)

### Intent

Answers "where does this network use public addresses on its own equipment, and what kind of interface carries each one" from the model. It is the evidence step before anyone touches the internet node's excluded subnets or explains an internet-exposure result.
`inspect-inventory` kind `ip_owner` answers for one address; this lists them all.

### Inputs

See the table of views above.

### Procedure

1. Read the snapshot; none ready is **unknown**.
2. Read every IPv4 interface address with its device type, interface type, VRF and description (paged, bounded). Keep the public ones (outside Forward's own non-public list).
3. Read the security zones, the devices' management IPs and, for firewall interfaces, the topology links and the device types on the other side, where the model has them (a failed read only weakens the roles, and is said so).
4. Give each address a role and the reason (`role_basis`), in this priority: management IP; a management name on the VRF, interface or description; a loopback interface; for a FIREWALL a security zone, then the interface description, name or VRF saying inside or outside. The context name (`-ext-dmz`, `-int-dmz`, `-lb`: `context_hint`) and the link's other side (`linked_to`) are shown and qualify the basis; they do not assign a role by themselves. Nothing else: the role stays `unknown`. Apply the filters, count by role, device type and VRF, and aggregate each role's addresses to the fewest exact CIDR blocks.
5. Return the summary and one page of rows (by role, then device). No match is **unknown**, never zero exposure.

### Limits worth stating

A role is inferred, not measured. A Cisco ASA has no security zone in Forward's model (its nameif and security level are not NQE fields), and most ASA firewalls are virtual contexts, so on an ASA-only estate customer-facing interfaces are mostly `unknown`: the `firewall_role_unknown` list is for review. management: the device's management IP, or a management name on the VRF, interface or description. loopback: a loopback interface. customer_facing and internet_facing: FIREWALL devices only, and only when a security zone, description or interface
name says so; otherwise unknown (nothing is guessed from the address). The candidate set is for the person to review: it never includes `internet_facing` or `unknown` addresses, the exclude list is prefix-based, it applies from the next processed snapshot, and an
address on a collected interface is located there before the internet node is considered, so excluding it need not change a device's internet-addressable flag (`plan-synthetic-device`, `reference/exposure.md`). IPv4 only; collected devices only.

### Evidence

One `nqe` item: `snapshot_id`, `interface_addresses_read`, `public_addresses`, `matching`, `distinct_addresses`, `devices`, `by_role`, `by_device_type`, `by_vrf`, `candidate_exclude` (per role: `addresses`, `cidr_count`, `cidrs`, `ownership_not_verified`), `prefix_groups` (the /8 and /16 spread of the candidates) and `largest_aggregates`, `firewall_role_unknown` (firewall addresses whose role stayed unknown, aggregated, grouped, labelled needs review: do not exclude blindly; never part of `candidate_exclude`), `unknown_by_group` (all unknown rows by device type, VRF and interface-name pattern with the top descriptions), `verify` (the before and after steps as concrete skill calls), `offset`, `addresses` (the page; rows may carry `context_hint` and `linked_to`) and `model_reads`. The skill does not check who owns a public prefix (no whois or registry lookup): excluding space the customer does not own only hides it.

### Next actions

`investigate-reachability` with `from: "internet"` to one address; `inspect-topology` (kind external) for what the internet node routes; `edit-internet-exclusions` (dry run first) only for public space the network routes internally; `plan-synthetic-device`.

## View trace_sources (the retired `find-trace-source` skill)

### Intent

A trace from a source that is blackholed at its first hop proves nothing about the destination. This skill picks sources that are not: it traces each candidate to a **control address** that must be reachable (the edge device's own interface
address, or a gateway) and reports which candidates arrive. It then hands you a source for `investigate-reachability`. Why and how to judge a synthetic-device change: `plan-synthetic-device`.

### Inputs

See the table of views above.

### Procedure

1. Read the snapshot; none ready is **unknown**.
2. List the devices that have an IPv4 routing table (in the VRF, when named), minus `exclude`, sorted by name. None is **unknown**.
3. Trace each of the first `candidates` from the device to `target_ip` (bounded: a few paths, ten seconds each) and classify the best path.
4. **ok** when at least one candidate is delivered, ranked delivered first and then by hop count (a farther source exercises more of the path); **failed** when none is.

### Limits worth stating

A delivered control means the source reaches the control address, **not** the real destination. The candidates are devices, not hosts: trace from a host with `investigate-reachability` `src_ip` when a host matters. Only the first `candidates` by name are traced.

### Evidence

One `path` item: `target_ip`, `vrf`, `candidates_traced`, `good`, `truncated` and `sources` (each: `device`, `control` classification, `hops`, `last_hop`, `delivered`).

### Next actions

`investigate-reachability` from the best source to the real destination.

## Running this skill

Give the inputs as one JSON object on stdin: `echo '{"network_id": "<id>", "vrf": "INET"}' | fwdctl run inspect-edge`; with a view, for example `{"network_id": "<id>", "view": "public_addresses", "role": "management"}` or `{"network_id": "<id>", "view": "trace_sources", "target_ip": "203.0.113.1"}`.
It needs the `fwdctl` binary and `FORWARD_URL`, `FORWARD_USERNAME`, `FORWARD_PASSWORD` in the environment. Read `status`
(`ok`, `failed`, `unknown`, `error`) and the `limits`; `unknown` is never a pass.
