# edit-change-set: inputs

`network_id`, `name`. Then `devices` (a list of `{device, commands}`, commands as one string of CLI text with newline-separated lines, or an array of lines) and/or `bgp_advertisements` (`device`,
`external_peer`, `prefix`, `next_hop`, optional `vrf`, `type`, `origin`, `local_pref`, `as_path`, `med`, `communities`). Optional:
`description`, `snapshot_id` (the base; default the newest processed one), `run` (predict it; needs `apply`), `apply` (default false).
`firewall_rules` stages security rule changes on a firewall (PAN-OS and similar): `{op: add, device, rule: {name, action, sourceZones, destinationZones, sourceAddresses, destinationAddresses, applications, services}, predecessor}` or `{op: remove, device, rule_id}`, in rulebase `scope_id` (default LOCAL) and `rulebase_id` (default PRIMARY); the result shows each firewall's staged rule diff, and `verify-change` predicts and judges it. Model new BGP originations with `bgp_advertisements`: Predict discards CLI `network` statements.

The dry run does the cheap checks the apply would fail on: an organization whose license lacks Predict (or a login without the permission) is reported as unknown with the licence limit, not as an ok dry run, and a device that is not in the base snapshot is refused by name.

`bgp_advertisements` entries take an `action`: `inject` (the default) or `modify` stage an advertisement (`next_hop` required; `type` is the PEER type, EBGP or IBGP, not the action, and a staged advertisement overrides a received one with the same key only when the peer type matches); `withdraw` stages the loss of a received advertisement (only `device`, `vrf`, `external_peer`, `prefix`); `restore` drops what is staged for that key. Use `withdraw` to model losing a peer OUTSIDE the snapshot, such as an ISP: a CLI `neighbor ... shutdown` removes the session from the prediction but the routes learned from it stay (the dry run warns when a CLI change contains one). `modify` and `withdraw` need received-advertisement collection on the device (`collectBgpAdvertisements` on, BGP table type BOTH or ADJ_RIB_IN); without it the route is left unchanged in the predicted snapshot and no warning is shown. `verify-change view preflight` counts the BGP devices that collect it.

`devices[]` takes exactly one of `commands` (CLI applied on top of the collected configuration, validated by Forward before it is kept) or `config` (the device's WHOLE replacement configuration, at most 2 MB; Forward stores it unchecked, so it is not validated here, and whether Predict can model the result depends on the device type). `firewall_rules[].op` is `add`, `remove`, `edit` (`rule_id` plus the rule's whole new definition in `rule`), `move` (`rule_id`, after `predecessor`; empty = first) or `discard` (drops that rule's staged add, edit, move or removal); only the local rulebase is editable.

`change_set_id` with `lifecycle` acts on an EXISTING change set instead of creating one, and does not combine with devices, bgp_advertisements, firewall_rules, snapshot_id or run: `{op: rename, name}` (and/or `description`), `{op: duplicate, name}`, `{op: delete}` (needs `confirm` = the change set id; there is no undo, duplicate first to keep a copy), `{op: discard_device, device}` (throws away that device's uncommitted edits) and `{op: restore_commit, commit_id}` (makes an earlier version current; the earlier versions stay in the history) and `{op: add_check, check, name?}`, `{op: edit_check, check_id, name? and/or check}` and `{op: remove_check, check_id}` (a change set carries checks of its own, evaluated on its base and each prediction: an intent check `{type: Isolation|Reachability|Existential, filters: <a path query as in path search>, noise_types?, header_fields_with_defaults?, return_path?}` or an NQE check `{type: NQE, query_id, params?}`; Forward runs a new check on the base before it answers, a check that fails to run still returns success with status ERROR or TIMEOUT, there is no server-side dry run so the dry run validates and plans, and Forward does not deduplicate; an edit cannot change a check's category; `return_path: SYMMETRIC` was measured to be stored but not asserted, so assert symmetry with one check per direction) and `{op: predict}` (starts a prediction of the change set and returns the predicted snapshot id at once, without waiting: wait with `fwdctl wait snapshot --network N --snapshot ID`, then read `verify-change` view `list`; a prediction is compute and leaves a predicted snapshot these skills cannot delete, so it is a dry run first like the rest). Each has a dry run. Predicted snapshots a change set already made are never touched.
Versions, copies, tags and filing (all dry run unless `apply`): `{op: commit, note}` saves the draft as a new version; `{op: edit_commit_note, commit_id, note}`; `{op: delete_commit, commit_id}` (needs `confirm` = the commit id; there is no undo); `{op: restore_commit_as_new, commit_id, name}` copies that version into a NEW change set (optionally `base_snapshot_id`); `{op: duplicate_to_network, target_network_id, name}` copies the change set to another network (needs the change-set permission on both; optionally `base_snapshot_id`); `{op: add_tags | remove_tags, tags}` and `{op: clear_tags}`; `{op: move_to_directory, directory}` with a path such as `/team/wan`. The versions, tags and directories are read with `verify-change` view `history`. Source-read from Forward (Preview routes), not run on a live Forward.

A full firewall rule (the shapes matter: address, user, application and service fields are objects, not lists; `{}` means any; `sourceZones` and `destinationZones` are plain lists, empty meaning any; `action` is `DENY`, `DROP` or `PERMIT` in upper case; omit `predecessor` to put the rule at the top; a list where an object belongs fails with a message naming the shape):

```json
{"network_id": "123", "name": "block dns to 8.8.8.8", "apply": true, "run": true,
 "firewall_rules": [{"op": "add", "device": "fw1",
   "rule": {"name": "block-8-8-8-8", "description": "test", "enabled": true, "action": "DENY",
            "sourceZones": ["trust"], "destinationZones": ["untrust"],
            "sourceAddresses": {}, "destinationAddresses": {"subnets": ["8.8.8.8/32"]},
            "sourceUsers": {}, "applications": {}, "services": {}}}]}
```

A rule staged in the local rulebase (the only editable one) is evaluated after any centrally managed pre-rules, so an earlier permit shadows a deny there, as it would on the device: check the pre-rules for the flow before expecting a block.

Read the effect from the rule diff the result carries (`firewall_rules_diff`) and the checks (a firewall rule compliance check moves by the violations the rule creates), not only from a path search on the predicted snapshot: a path search shows a flow the rule blocks only if that flow crosses the firewall, and `verify-change` view `paths` needs advanced reachability on the base (`edit-advanced-reachability`).

Commands are applied in configuration mode already, so a leading `configure terminal` (or `conf t`) line of a device's commands, as a patch file often starts with, is dropped and the result says so; Forward rejects it as an invalid command. A rejected line is named in the finding with its number, its text and Forward's parser message (up to three). With `run: true` the result names the predicted snapshot as soon as the prediction starts (`predicted_snapshot_id` in the evidence); if the wait ends before it finishes the finding says whether it is still running (wait for it with `fwdctl wait snapshot --network N --snapshot ID`) or ended in a failed state; the wait never cancels a prediction. There is no snapshot-level cancel in Forward; `edit-jobs` (ADMINISTER_SYSTEM, dry run first) cancels backend jobs that have run past a threshold.

`directory_op` (instead of a change set or lifecycle) organises the directories change sets are filed under: `{op: add, path: /team, name: wan}`, `{op: rename, path, name}`, `{op: move, path, to}`, `{op: delete, path}` (its change sets are kept, unfiled) or `{op: delete, path, also_delete_change_sets: true}` (deletes them too, no undo, `confirm` = the path). Dry run unless `apply`. Preview routes, source-read; the apply path is fixture-tested only, not run on a live Forward.

Also lifecycle `{op: prettify, device, commands}` (returns Forward's formatting, changes nothing), `{op: export_zip, path}` (writes the head version to a NEW local .zip file; Forward needs the org property PREDICT_DIFF_INSIGHT_ENHANCEMENTS and a committed version) and top-level `bulk_delete: [ids]` (several change sets at once; irreversible; `confirm` = how many; an id the network lacks makes the whole call unknown and deletes nothing).
