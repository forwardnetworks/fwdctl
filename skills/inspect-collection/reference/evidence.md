# Evidence fields of inspect-collection, by view

One `collection` item. migration: `by_category`, `by_effective_type`, `controllers` (`name`, `address`, `devices`, `controller_kind` from the devices' types, `device_names`, `found_by` (the devices' last connectivity test), `classic_record` and `address_confirmed_by_a_record` when a classic device has that host (its type, CLI, HTTP and SNMP login ids, jump server and collector: an address no record confirms and no name is not established), and `suggested_migrate`: a ready `edit-source` `controller_setup` `migrate` input (the setup name inside `definition`) for a pilot of up to 25 devices, a `warning` that migrate deletes the classic records, and `credential_hints` (for a device with no login recorded, the logins its same-/24 siblings use); devices whose test reported no controller (Versa edges) are linked to the network's only controller record of their category and `found_by` says so; `limit` caps the controllers), `migration_plan` (the migrate input for ALL counted devices, built from the records: each as a managed entry with type, host, login ids, jump server, port and collection options restated; `controllers` left empty to fill from the controllers you chose; `review` lists the vEdges whose collect is not false, the devices with no login and the devices no controller test reported; a starting point to review, nothing applied; checked read-only against one real network by a field session: identical to the input they had built by hand from the 85 device rows, and the review block named the right vEdges), `edge_coverage` (for the IOS XE SD-WAN edges: read from each edge's `sdwan_control_connections.txt` in the newest processed snapshot, vsmart rows with STATE up; the minimal cover of vSmart system IPs, the edges with no file, no vsmart rows or none up, and the edges the wizard's controllers do not reach; checked read-only against one real network by a field session: it matched their hand computation), `devices` (every counted device: `name`, `effective_type`, `category`, `controllers`, and from its classic record `host`, `cli_credential_id`, `jump_server_id`, `collector_id`; at least 50 shown), `credential_candidates` (the auto-associate CLI logins, id, name, username and `name_suggests_vendor` when the login's name contains a vendor of the counted devices; ids and names only, never a secret: the login that worked is not recorded, so a pilot connectivity test is needed), `devices_counted`, `devices_read`, `devices_without_test_result`; status Failed when any device is counted. status: `newest_snapshot` (`id`, `kind`, `origin`), `running`, `progress`, `recent_tasks`, `collector`, `devices`, `failed_devices`. config: `devices` (paged), `device_count`, `devices_not_collected`, `endpoint_count`, `endpoints_by_type_and_profile`, `endpoints` (paged by limit and offset, each with its `profile_id`), `endpoint_profiles` (the profiles those endpoints use: an SNMP profile's OID sets and custom OIDs, a CLI profile's commands (and `collects`: true only if Forward's approved-command check approves ALL of its custom, detector and name-detector commands, with `unapproved_commands` listed; `unknown` when the check is refused, since it needs the manage-endpoint-profiles permission, so a read-only login sees unknown, not a pass), an HTTP profile's requests and header names, never header values), `collection_schedules` (each: enabled, time zone, and either the times and days or the period; no next run is returned by Forward), `approved_cli_commands` (count, and whether the organization uploaded its own list: a CLI command runs only if approved), `jump_servers`, `proxies`, `cloud_setups` (name, type, whether it collects, its regions and each region's last connectivity test), `summary` (counts over the WHOLE device list, whatever page is shown: by type, without a CLI credential, SNMP collection on; Forward's device records carry no vendor, jump server or creation time, so those cannot be counted, and the per-collection device counts are in `investigate-collection-failure` view `history`), the collector's configured `concurrency` in the status view's `collector` block (128 when unset, said so), `data_files` (name, `nqe_name`, type, description, whether attached to this network, how many networks in all), and with `data_file` given, `data_file_schema` (Forward's inferred NQE type, data format, warnings, errors and the whole stored content (`content`, up to 200,000 characters) only with `include_content`, so a file can be saved before edit-data-file replaces it); `data_connectors` (name, base URL, endpoint count, whether it collects, status in the latest processed snapshot), and with `data_connector` given, `data_connector_detail` (its endpoints, proxy/collector and last stored connectivity test). Profiles are organization-wide and Forward's API can edit them (SNMP custom OIDs, CLI commands, HTTP requests); no skill does, since a change applies to every network and collector. A data file attached to a network is read in NQE as `network.extensions.<nqe_name>`, a record `{status: OK | MISSING | INVALID_DATA, value}`; MISSING means no snapshot since attachment has carried it yet. A data connector is per-network (not organization-wide like a data file) and is read in NQE as `network.dataConnectors`; `edit-data-connector` manages it.
