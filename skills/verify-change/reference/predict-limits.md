# What Predict does and does not model

Read before saying a change set is safe, or before trusting a check on a predicted snapshot. **Unverified:** these limits were measured on one network by a colleague and are not reproduced here; the schema facts are checked against the NQE schema, the behaviours are not. Confirm with a read-only comparison before stating one as fact.

- **BGP RIB can be stale on a predicted snapshot.** Fields such as `activeRoute` and `adjRibInPost` may carry over from the base snapshot rather than being recomputed. An NQE check that reads them says nothing about the change. Read the forwarding table (`afts`) or run a path search on the predicted snapshot instead.
- **Advertisements are not policy.** Staging or removing a BGP advertisement cannot show a change whose effect comes from policy (a route-map, a local preference) re-selecting an existing route. A CLI change set that edits the policy is the thing to predict; say what was and was not modelled.
- **The device you cut may not re-select its own best path.** If a check starts from the device whose route you changed, test from the far side of the change as well.
- **Return path.** A check option that asks for a symmetric return path may be accepted without being asserted. Compare the two directions yourself (`investigate-reachability`, `reference/reading-paths.md`).
- **`unknown` stays unknown.** A check that needs additional processing is not a pass, and a predicted snapshot that is not yet ready is not an empty result: wait for it, then read.

## What Forward's source says about how Predict works (read from source, NOT confirmed on a live Forward)

Read from a Forward source tree (1.0.0-261031 build); the claims marked [I] are inference. Say "per Forward's source" when you rely on one.

- **How it predicts.** Predict writes the predicted config TEXT over the device config in a forked snapshot, parses it with the normal vendor parser, runs protocol modelling and regenerates the state files.
- **Which OSes take CLI changes.** Only IOS, IOS-XE, NX-OS, IOS-XR, ASA, EOS, Junos and SRX have a command parser. `verify-change` view `commands` (no `os`) lists the OSes Forward reports; with `os` it lists the commands Predict accepts. An empty list is normal for PAN-OS (security rules, not commands) and Junos (checked in code, no command tree); a 500 is a Forward bug that hits every protocol on cisco_ios, cisco_ios_xe, cisco_ios_xr, cisco_nxos, cisco_asa and arista_eos (its command-tree printer has no cycle guard, so it overflows the stack; same code in the primary, stable and master source), and is unknown, not "no commands". Only juniper_srx answers, so do not use this view to learn what an OS accepts.
- **PAN-OS.** CLI is never sent (a CLI change set fails with "OS not supported"). Changes go through the structured security rules, and only the local rulebase in the local scope is editable. Whole-config upload (save device config) works for any vendor including PAN-OS and bypasses every predictor.
- **What is modelled is switched by org properties.** `PREDICT_MODELING` is the master; BGP, OSPF, IS-IS, OMP and static routes plus interface shutdown (the CONFIG protocol) each have their own property (`PREDICT_MODEL_BGP`, `_OSPF`, `_ISIS`, `_OMP`, `_CONFIG`). With `PREDICT_MODEL_CONFIG` false the predicted config text still changes (a config-text NQE check sees it) but the RIB and AFT do not [I]. EIGRP, RIP and STP appear in protocol lists but are never modelled. `PREDICT_CONFIG_ONLY` is an org mode that applies the config but copies state from the base snapshot. Read the properties with `inspect-platform` (settings) before saying a protocol change was modelled.
- **OMP and IS-IS.** Both org properties (`PREDICT_MODEL_OMP`, `PREDICT_MODEL_ISIS`) default off. Their data is parsed when a snapshot is processed (whether an old snapshot is re-parsed when the property changes is unverified). OMP is Cisco IOS-XE SD-WAN only. Forward has no node-read route for OMP or IS-IS state and no allowed-commands list for them (the command trees that would list them hit the renderer bug above). Read from the SDK session's reading of Forward's source, not run live.
- **Reading a prediction (observed on live runs, reported by another session).** A prediction over a stale base can fail with no reason: reprocess the base first. The protocol-modeling affected-devices list holds every device with an L3 address, not only the changed ones, so it is not the change's blast radius. Deleting a change set (or a directory deep) also deletes its predicted snapshots, which then 404: read what you need first. Validation errors seen live were all INVALID, PAN-OS validates nothing, and EOS flags some real commands: INVALID is evidence for review, not proof.
- **Command validation is advisory.** Validation reports problems but nothing rejects a bad line at staging, and an empty result proves nothing.
- **Security rules (PAN-OS and firewall rules).** Actions in Forward are DENY, DROP, PERMIT, RESET_CLIENT, RESET_CLIENT_AND_SERVER and RESET_SERVER, but on PAN-OS (observed on a live run) DROP predicts as DENY and any RESET_ rule stages and then breaks the prediction (the predicted rulebase empties, every flow permitted), so `edit-change-set` refuses RESET_. "Any" is every field empty when you write a rule; read back it appears as the zone `any` and predefined `any` objects, so compare by meaning. That DROP and RESET_ are accepted by the rule API on a real PAN-OS rulebase is NOT measured live. A rule added through the API is given a UUID; a rule with no UUID is ignored only when the config is predicted. An edit is a remove plus an add inside Forward but the edited rule keeps its UUID and position, so treat it as an in-place edit. Only the local scope's primary rulebase is editable. Logging is not modelled (an existing rule keeps its baseline logging, a new rule gets none). The rule editor works without the NQE security-rules feature flag, which gates only the NQE view of PAN-OS rules. The SDK's rule definition does not yet carry IP ranges, dynamic address objects, regions, schedules or URL objects.
- **Added static routes and Null0.** An added static route is modelled by the CONFIG pipeline only when `PREDICT_MODEL_CONFIG` (and `PREDICT_MODELING`) is on: off by default in 26.10.4, on by default in 26.11.0. The pipeline covers EOS, ASA, IOS, IOS-XE, IOS-XR, NX-OS, NX-OS ACI, FortiOS, Junos, SRX, Meraki MX and PAN-OS. A route to Null0 has no special case in the source, and how it becomes a forwarding entry or a drop is not established; it has not been tested. When a predicted snapshot still forwards past an added Null0 route, check the flag first. Then add an ordinary static route with a real next hop on the same device: if that one is missing from the predicted forwarding table too, the pipeline is off; if only the Null0 one is missing, it is the null-interface handling (a Forward question, with the config line and build).
- **ACL edits are not a Predict change.** No vendor has an ACL predict pipeline in 26.10.4, 26.11.0 or master, so an ACL line (an ASA `access-list ... extended permit ...`, any vendor's ACL) is not a supported change, and a rejection of it as invalid is consistent with that. ASA does have a command grammar, for its BGP, CONFIG (static and direct routes) and IS-IS changes.
- **Checking a static-route change.** The NQE model exposes INSTALLED static routes (the forwarding table) and the config text, not configured static routes, and Forward's internal configured-state model is not reachable from the API. Check a static-route change by the installed route in the predicted snapshot plus a config-text match, and read the device back after a real change.

Say in the answer which of these applied, and which flows were not tested.
