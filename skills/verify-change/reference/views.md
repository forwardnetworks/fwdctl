# verify-change: views and procedure (reference)

The full text of each view and the verify procedure. SKILL.md carries the one-line version.

## Views

`view` picks the question; an input that belongs to another view is rejected by name. `verify` (the default; `verdict` is the same view) judges a change; `impact` measures how far it reaches (with a change set it also checks each staged BGP advertisement against the forwarding entry it should move on its device, base against predicted, and says `recorded_but_unchanged` when a withdraw or inject was recorded and the entry did not move; the difference areas, subnet connectivity, and a routing area: BGP neighbor sessions removed, added or changed state, and IPv4/IPv6 route and next-hop counts per device and VRF, with `device` that device's per-prefix route changes; a route change on a device the change set does not edit is flagged as possible baseline drift, because a predicted snapshot can differ from the collected base with no change staged); `preflight` is the Predict demo checklist in one call: the scope plus the release, whether received BGP advertisements are collected on the BGP devices (modify and withdraw do nothing, silently, without it), whether the base snapshot is a fresh collection and the existing change sets; `scope` answers "what of this network can Predict model on this release" (the license facet, the BGP families in config that Predict does not model, the platforms where propagation stops, every `predict_*` flag the login can read (`flags`, each with its source: read from the tenant, or the default of the release when it cannot be read) and whether OSPF and static are re-propagated from those flags; it reads and judges no change); `list` lists the network's change sets (id, name, base snapshot, `devices_edited` = the devices of the last COMMITTED version, with `draft_devices` for a change set that is staged but has nothing committed yet; none is an answer, an unlicensed organization is a licence limit, not an empty list); `describe` reads a change set that has not been run (each prediction carries `finished`: a predicted snapshot reports UNPROCESSED while it is still being created or computed, so only PROCESSED, FAILED, CANCELED and TIMED_OUT are final; the devices it edits and, per device, what is staged are read from its head commit and its draft (the change-set list never carries them): the number of CLI lines, a whole-config replacement, pending firewall rule changes, and the BGP advertisements injected or modified and the ones withdrawn, so a withdraw can be confirmed as recorded; `draft_devices` counts this login's uncommitted draft); `paths` is the GUI's "view interesting paths": it ranks sampled paths through firewalls and load balancers best score first, top 10 per kind, with each path's processing stages (IN_ACL, XLATE_DNAT, MPLS, ...), hop count and the decoded path query, on `after_snapshot_id` or on a change set's predicted snapshot (`change_set_id`), so the same question can be asked before and after a change. It needs the path-search licence and advanced reachability on the snapshot (otherwise unknown, naming `edit-advanced-reachability`), runs synchronously for at most `connectivity_timeout_seconds` per kind (default 45, at most 300), and samples: a path not listed is not proven absent.

## Procedure

1. Resolve before and after. For a change set, before is its base snapshot and after is its
   newest processed predicted snapshot. If there is none and `run_predict` is not set, stop:
   `unknown` (running Predict costs compute, so it is opt-in). Both snapshots must be processed.
2. Read the subnet-connectivity diff **once it has settled**. A read right after a prediction
   returns all zeros with `is_partial_result` set; those zeros mean "not finished". Zero
   subnet pairs compared means nothing was compared, not that nothing changed.
3. Compare checks before and after. A check with more violations, or one that went from
   PASS to FAIL/ERROR/TIMEOUT, is a **regression**. This needs no statement of intent.
4. Evaluate each expectation with a path search on the **after** snapshot.
   `delivered` needs a delivered path. `blocked` needs a real failure and no delivered path
   from a completed search. No paths, a timeout or an incomplete model is undetermined.
5. Decide:
   - Any regression, or any unmet expectation: **failed**.
   - Expectations given, all met, no regressions: **ok**.
   - Any expectation undetermined (and nothing failed), or no expectations given: **unknown**.
     Without a stated intent the skill reports the impact but does not judge it.

**view impact.** Takes the same selector (`change_set_id`, or before and after snapshots) but no expectations. It counts the differences in every area Forward can count and compares subnet connectivity, then reports the extent. It never judges and never reports a regression: use the default view for a verdict. Areas that were not measured are named in the limits, and nothing is said about them. When the ACL area changed it also names the devices whose ACLs changed (`acl_devices`, the most changed first, with rules added, deleted and modified); with `device` it lists that device's changed ACL rules (`acl_changes`: added, deleted or modified, with action, name, where it applies, match conditions and the configuration lines, and for a modified rule what it was). A rule diff is evidence of what changed, not a verdict on whether it is safe.

**view describe.** Each check row carries its `definition` and `add_check`, the same definition in the keys `edit-change-set` lifecycle `add_check` takes, so a check read here is added to another change set (or network) unchanged; an unnamed NQE check is named by its query. Reads a change set without touching it (it lists each check attached to the change set as `checks`: name, type and note, status and violations on the base and on the newest prediction; a prediction that has not finished carries `processing`: the stage computing now, its objects, elapsed against Forward's estimate and `over_estimate`, so a stuck one shows early; `list` does the same): it never runs a prediction, stages a command or commits (`verify-change` view verify runs and compares, `edit-change-set` builds). Inputs: `network_id`, `change_set_id` (required), and optionally `device` (a firewall whose rule diff to include); it takes none of the view verify inputs.

1. Find the change set in the network. If it is not there the answer is **unknown**, not an error in the network.
2. List its predicted snapshots and take the newest PROCESSED one.
3. Read the change set's checks on the base snapshot and on that prediction; a check that is bad on the prediction and was not bad on the base, or has more violations, got worse.
4. With `device`, read the rule diff and count the entries by kind of change.
5. **failed** when any check got worse on the prediction; **ok** when a prediction was read and no check got worse; **unknown** when the change set has not been predicted (run view verify with `run_predict`) or its prediction checks could not be read. A change set with no checks attached says so in the limits, since an unchanged verdict then proves nothing. Evidence is one `predict` item with `devices_edited`, `predictions`, `checks_that_got_worse` and, with `device`, `security_rules_diff`.

## view ai_summary

Forward's AI explains a difference in words. It is the differential analysis: what changed, what it does, why checks fail. It is generation, not a read: Forward's AI service receives the diff, so the view is the opt-in and nothing calls it otherwise.

- Inputs: `change_set_id` (the base and the newest prediction), or `before_snapshot_id` and `after_snapshot_id` (any two snapshots, a prediction against its base included), and `summary_kind`: `impact` (default: what the change does to the network), `config` (what changed in the configurations), `overview` (a name, description and tags Forward proposes for a change set; needs `change_set_id`), `failure` (why checks fail; needs VIEW_CHECK_DIFFS and PREDICT_FAILURE_SUMMARY_ASSIST; partial while checks still process).
- Needs the organization properties `AI_ALLOWED` and `PREDICT_AI_ASSIST` (the failure summary: `PREDICT_FAILURE_SUMMARY_ASSIST`). They are read first; an explicit false is `unknown` with the property named, and nothing is sent.
- The result carries the text, `generated_by: Forward AI` and the two snapshot ids, and limits that say it is generated text and not a measurement. Check it against `impact` (the counted differences). Forward's AI may be off for an organization; the deterministic views work without it.

## view impact: Forward's own diff tables (`native_diffs`)

Besides the counted differences and the routing area, `impact` reads the tables the GUI's Compare shows and puts them in one `native_diffs` item: **ARP, MAC and NAT** (a count, and the devices that changed with their ADDED, DELETED, MODIFIED and UNCHANGED counts, most changed first, capped), **L3 routing** (Forward's route diff: the changed devices and its summary; with `device`, that device's route diff), the **vulnerability diff** (new CVEs, new exposed vulnerable devices when internet exposure is computed, and the improvements side when the organization property PREDICT_DIFF_INSIGHT_ENHANCEMENTS is on) and whether a **routing loop** was introduced or resolved (0 or 1, not a count; complete false is unknown).

Each read stands alone: one that is refused (VIEW_ARP_DIFFS, VIEW_MAC_DIFFS, VIEW_NAT_DIFFS, VIEW_ROUTE_DIFFS, VIEW_CVE_DIFFS, the security licence facet) is named in the limits and the others still count. Forward computes and caches the L3 diff on its first read, which can be slow on a large network. Forward's L3 table and the model's route counts can disagree: on snapshots built from configs alone (no collected routing table) the L3 table was empty even for an added static route, because it compares the routing tables as collected; when they disagree the limits say so, and the counted differences and per-prefix lists are the ones to trust.

**Where a route diff sits in the result, and its keys.** Two items, with different shapes. (1) `nativeDiffs` (`detail.native_diffs.l3`): `devices` (each `{deviceName, hasConfigChange, stats}`, `stats` holding ADDED, DELETED and MODIFIED counts), `devices_changed`, `summary` (Forward's JSON as sent) and, with `device`, `device_detail` = `{device, diff}`. `diff` is Forward's raw JSON for that device (routes added, removed and changed, with next hops); its entry field names are not recorded here (unverified), so read them from a live result rather than assuming. (2) `routingDelta`: with `device`, the key `prefix_changes_<device>` holds typed rows `{vrf, prefix, change, next_hops_before, next_hops_after}`, where `change` is `added`, `removed` or `next hops changed`, IPv4 forwarding entries only, sorted by VRF and prefix, at most 50 rows followed by one `{note}` row ("N of M prefix changes shown"). With no note row the list is the device's complete IPv4 forwarding-entry diff across its VRFs: next hops are compared as a sorted list of next-hop addresses, a null address counting as the text "<nil>" (a connected or local entry has [null], so it normally shows only as added or removed, but null to an address, or a different number of nulls, shows as "next hops changed"); rows are text, not arrays, and sorted as text by VRF then prefix; when nothing changed the key is present and null, and a table of more than 200,000 entries is not diffed (the key is absent and a limit says why). An absent key with a limit means the read failed, not that nothing changed.

`scope` and `preflight` count SD-WAN devices (`sdwan` in the scope detail): Viptela devices by OS name, and IOS-XE devices that collected `SDWAN_OMP_ROUTES` output (`show sdwan omp routes`), which is how an IOS-XE device in SD-WAN mode shows. They report whether `predict_model_omp` is on. Predict does not recompute the SD-WAN overlay (OMP) on 26.9; the OMP engine is behind the flag and not validated. An IOS-XE device whose SD-WAN output was not collected is not counted (a limit says so).

## view history, config and affected (Predict change sets)

- `history` (`change_set_id`; optional `commit_id` for one version): the change set's saved versions newest first (commit id, note, who and when, how many devices each edits), `newest_version`, a summary (name, base snapshot, tags, and the linked ServiceNow change requests: number and sys_id, and for the first 10 the state, URL, impact, priority and attachments read live from ServiceNow through Forward; a request that cannot be read says why) and the directory it is filed in (left out, with a limit, when the organization has directories off). Use it to choose the `commit_id` for `edit-change-set` lifecycle restore_commit, restore_commit_as_new, edit_commit_note or delete_commit. An uncommitted draft is not a version: `describe` shows the draft.
- `config` (`change_set_id`, `device`; optional `commit_id`): that device's configuration in the draft (default) or in one saved version, as lines (the first 300). A device the change set does not edit has none of its own.
- `affected` (`after_snapshot_id`, a predicted snapshot): the devices Forward's protocol-modelling job re-computed for the prediction. This can be wider than the devices the change set edits, and Forward keeps no list for a base snapshot (unknown).
All three are Preview routes read from Forward's source and its Go SDK; not run on a live Forward.
- `bgp_diffs` (`change_set_id`, `device`; optional `commit_id`): what the staged BGP advertisements change on the device against the base snapshot, in the draft or one version. Zero diffs means no staged advertisement change on that device, not that the device is unaffected.
- `objects` (`change_set_id`, `device`, `object_kind`): a firewall's address/application/url/service/user objects, groups or zones as the change set holds them, in Forward's own JSON.
- `checks` (`change_set_id`): the NQE checks added to the change set (their results are in `describe`).
- `commands`: without `os`, the vendor OSes Predict models and the protocols; with `os` (and `protocol`, default CONFIG), the commands Predict accepts, as Forward renders its command tree. Check it before staging a command Predict may not model.
- `affected` also returns `protocol_modeling_done` (null when the status cannot be read: Forward's status route needs the network ADMIN role, so a lower role gets the devices without it); a failed modelling job reads false too, so bound any wait.

## view model_check (experimental): how well Predict models this snapshot

The question it answers: "before I predict anything on this network, how closely does Predict's model reproduce what the snapshot collected?" It takes `network_id` and optionally `after_snapshot_id` (a collected snapshot; the latest processed one when left out) and returns Forward's own score as it sends it: `detail.score` (overall) and `detail.scores_by_protocol` (one entry per protocol, for example BGP). The finding quotes precision, recall and f1 when the score carries them. It does not accept a change set or a prediction (Forward's check runs on a base snapshot).

The scores are `precision`, `recall` and `f1` as percentages from 0 to 100: precision is matching entries over the entries Predict modelled, recall is matching entries over the entries collected, f1 their harmonic mean. The overall score covers only the protocols enabled by the PREDICT_MODEL_* organization properties (BGP, OSPF, CONFIG, OMP, IS_IS), so on a default setup a low recall can reflect how little of the collected state is modelled rather than model error (not verified; read it next to view `scope`). A protocol key appears only if some device counted at least one entry for it: a missing key means nothing was counted, and a key with zeros means entries existed and none matched (BGP counts MPLS entries; the keys that can appear are BGP, OSPF, CONFIG, OMP and IS_IS). The entry counts behind the scores are not returned.

Read it with these limits. It calls a Forward `/api/internal/` route that is not in the published API (read from Forward's source by the SDK session), so it may change without notice; it is refused under `FWDCTL_ALLOW_NETWORKS` (that route is not scoped to a network). It needs the MANAGE_PROTOCOL_MODELING permission, which belongs to the network ADMIN role, and the Predict licence (without them the result is unknown and says so). It recomputes on every call: no result is stored and no audit event is written, but Forward may start its protocol-modelling jobs for the snapshot and cache derived results, and the first call on a snapshot can take minutes (the SDK waits up to 30 minutes; a timeout is unknown). A score that is zero in every field cannot be told from a snapshot with nothing to compare (no collected routing state, or nothing modelled), so it is returned as unknown, never as a result. Seen live on a 26.10 tenant: a collected snapshot answered in about a second with only BGP in the per-protocol scores.
